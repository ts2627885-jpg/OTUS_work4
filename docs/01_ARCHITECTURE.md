# АЗС-Пульт: архитектура решения

Состояние на 13.10.2026. Документ описывает то, что реально работает. Старые документы в `docs/` (AZS_Pult_FullStack_Solution.md, ARCHITECTURE.md в корне и др.) исторические.

## 1. Состав системы

```
Браузер
  │  HTTP /api (JSON, Bearer-токен)
  ▼
Frontend: Vue 3 + Vite + Pinia + Axios + Element Plus        (frontend/)
  │  dev: прокси Vite /api → backend;  prod: nginx → backend
  ▼
Backend: Express 4 + TypeScript                              (backend/)
  │  pg (пул соединений), роль приложения azs_app (без BYPASSRLS)
  ▼
PostgreSQL                                                   (схемы public и azs)
  • боевая база: Supabase (PostgreSQL 17)
  • self-hosted: контейнер из db/ (PostgreSQL 18)
```

Внешних сервисов нет: авторизация собственная (JWT), пользователи хранятся в `public.users`.

## 2. Frontend

- `src/api/` — модули запросов: `client.js` (Axios, токен, перехват 401), `azs.js`, `analytics.js` (включая список цен), `admin.js`, `dashboard.js`, `recommendations.js`, `import.js`, `auth.js`.
- `src/composables/` — хуки для данных: `useRequest` (загрузка и ошибка, `errorMessage` переводит ошибки в понятные тексты), `useMutation` (отправка), `useStations`, `useRecommendations`, `useImport`.
- `src/views/` — страницы: дашборд, станции (список и карточка), аналитика, рекомендации, данные и импорт, администрирование, вход и регистрация.
- `src/mocks/` — моки для работы без бэкенда (`npm run dev:mock`), в обычном режиме не используются.

Фронтенд обращается только к API. Прямого доступа к Supabase из браузера нет.

## 3. Backend

Слои (`backend/src/`):

| Слой | Папка | Что делает |
|---|---|---|
| Точка входа и маршруты | `server.ts`, `routes/` | Регистрация эндпоинтов, middleware, старт сервера |
| Контроллеры | `controllers/` | Разбор запроса и ответ (сейчас — аутентификация) |
| Сервисы | `services/` | Расчёты и бизнес-правила: правила цен, эластичность, аналитика, рекомендации, импорт, резервные копии, доступ, планы теста |
| Репозитории | `repositories/` | Доступ к таблице пользователей |
| Middleware | `middleware/` | JWT, роли, контекст базы (RLS), обработчик ошибок |
| Конфигурация | `config/` | Пул соединений, контекст запроса к базе |
| Утилиты | `utils/` | Логгер, Joi-валидация, классы ошибок, приёмник логов в базу |

Ключевые сквозные механизмы:

- **Аутентификация.** `POST /api/auth/login` выдаёт JWT (срок по `JWT_EXPIRES_IN`). Токен обязателен для всех маршрутов, кроме входа, регистрации и `/api/health`. Ошибки: 401 без токена или при неверном токене.
- **Роли и доступ к станциям.** Роли: `admin`, `manager`, `analyst`, `viewer`. Admin видит и меняет всё. Manager видит и меняет только назначенные станции (`azs_access`). Analyst и viewer только читают. Проверки выполняются в коде (`access.service.ts`, `requireRole`).
- **Контекст базы для RLS.** На каждый запрос `/api` берётся отдельное соединение, в нём задаются `app.role` и `app.user_id`. Политики в базе ограничивают строки по роли и станции (миграции 010, 012–014). Без контекста строк нет.
- **Единый формат ошибок.** `{ "success": false, "error": "текст", "code": "КОД" }`. Ошибки клиента (400, 401, 403, 404, 409) с понятным текстом, ошибки сервера (500) — без внутренних деталей.
- **Логи.** Все записи пишутся в `logs/app-ГГГГ-ММ-ДД.log` (JSON по строке, хранение 90 дней). При `LOG_TO_DB=true` предупреждения и ошибки дополнительно попадают в таблицу `app_logs`.

## 4. База данных

### Схема `public` — данные приложения

Основные таблицы: `users`, `azs`, `azs_access`, `prices`, `price_history`, `recommendations`, `sales_data`, `weather_data`, `competitor_prices`, `price_test_plan`, `app_settings`, `audit_logs`, `login_logs`, `import_history`, `app_logs`. Представления: `v_azs_revenue_summary`, `v_price_trends`, `v_recommendations_stats`, `user_names` (только id и имя).

### Схема `azs` — аналитика

Загружается из CSV пайплайном (`_data/_BD/pipeline/`) и импортом через API: `station`, `fuel_type`, `calendar`, `competitor`, `competitor_price`, `fuel_daily`, `station_daily`, `traffic_daily`, `weather_daily`, `shop_product`, `shop_sales_daily`, `promotion`. Приложение читает эти данные и синхронизирует станции в `public.azs` (`sync_public.sql`).

### Миграции

Файлы `backend/src/database/migrations/001…017`. Применяются командой `npm run migrate` в папке `backend`. Учёт — таблица `schema_migrations` (версия и checksum). Миграции 009 и 016 выдают права роли `azs_app` на схему `azs` и выполняются, только если схема существует.

### Роли в базе

| Роль | Назначение | Особенности |
|---|---|---|
| `postgres` / владелец | миграции, пайплайн | обходит RLS |
| `azs_app` | приложение | не суперпользователь, без `BYPASSRLS`, действуют политики |
| `anon`, `authenticated` (Supabase) | публичный API Supabase | доступ отозван миграцией 011 |
| роль бэкапа (`BACKUP_DB_USER`) | резервные копии | обходит RLS, иначе копия была бы неполной |

## 5. Поток данных

1. **Импорт CSV** (`POST /api/import/csv`, admin или manager): тип файла определяется по заголовкам, данные пишутся в `azs` (upsert), затем синхронизируется `public`, пересчитываются рекомендации. Резервная копия делается до записи.
2. **Расчёт правил** (`GET /api/analysis/rules`, `POST /api/recommendations/generate`): читает `azs`, считает эластичность и правила. Результат кэшируется по версии данных (количество строк и даты таблиц) и по настройкам, кэш сбрасывается после импорта и через 10 минут. Холодный расчёт занимает около 10 секунд.
3. **Рекомендации**: создаются правилами (с дедупликацией по `dedupe_key`), закрываются вручную (`complete`) или автоматически при пересчёте.

## 6. Резервные копии и обслуживание

- `POST /api/admin/backup` (admin): `pg_dump` в формате custom в `backend/backups`. Копируются схемы `public` и `azs`. Хранятся последние `KEEP_BACKUPS` копий, неполный файл при ошибке удаляется. Таймаут — 5 минут.
- Копия делается от роли `BACKUP_DB_USER` (см. `02_DEPLOYMENT.md`).
- Скрипты (`scripts/`):
  - `api-test.mjs` — проверка всех эндпоинтов по ролям и ошибкам (только чтение и отказы);
  - `api-write-test.mjs` — проверка записей, работает только с тестовым бэкендом на `localhost:3005`;
  - `analyze-logs.mjs` — сводка по журналам (уровни, ошибки по путям, частые сообщения);
  - `db-health-check.ps1` — проверка бэкенда и базы, перезапуск бэкенда при падении (регистрация задания: `register-health-check.ps1`).

## 7. Известные ограничения

- **Соединение с базой.** Пулер Supabase иногда не отвечает дольше таймаута (по умолчанию 20 с). Тогда ответ будет 500 с текстом «Внутренняя ошибка сервера» и записью в журнале.
- **Холодный расчёт правил** — около 10 секунд. Прогрев кэша при старте выполняется в фоне (до трёх попыток).
- **План теста цен** привязан к станции через `azs_id`, миграция 012. Записи планов до этой миграции без `azs_id` видны только admin.
- **Пароли тестовых учётных записей** в публичном репозитории: см. отдельную заметку в `API.md`, раздел «Безопасность».
