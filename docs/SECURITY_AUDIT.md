## Защита от XSS, CSRF, SQL-инъекций

### SQL-инъекции
- Все запросы к БД параметризованы (`$1`, `$2`…). Конкатенации пользовательского ввода в SQL не найдено.
- Semgrep с правилами OWASP запускается в CI (job `security`) и падает при находках уровня ERROR.

### XSS
- **Content-Security-Policy** в `vercel.json`: `default-src 'self'`; скрипты только со своего домена (`script-src 'self'`), запросы только к своему домену (`connect-src 'self'`), `object-src 'none'`, `frame-ancestors 'none'`. Для стилей разрешены inline-стили (`style-src 'self' 'unsafe-inline'`): Element Plus использует их.
- **`X-Content-Type-Options: nosniff`**, **`X-Frame-Options: DENY`**, **`Referrer-Policy: strict-origin-when-cross-origin`**, **`Permissions-Policy`** (камера, микрофон, геолокация, платежи отключены), **HSTS**.
- В линтере фронтенда включены правила `vue/no-v-html`, `no-eval`, `no-implied-eval`, `no-new-func` (ошибки). Сейчас `v-html` в `frontend/src` не используется.
- Backend отдаёт JSON; `helmet` добавляет свои заголовки.

### CSRF
- Аутентификация по заголовку `Authorization: Bearer`. Браузер не отправляет такой заголовок автоматически, поэтому классическая CSRF-атака на API не работает.
- Cookies для аутентификации не используются. Если это изменится (например, переход на httpOnly-cookie из пункта 14), понадобится CSRF-токен или проверка `Origin`.
- CORS разрешает только адреса из `FRONTEND_URL`.

### Аутентификация и перебор
- Ограничение входа: 10 неудачных попыток за 15 минут с одного адреса (`express-rate-limit`). Успешные входы не считаются.
- Одинаковое сообщение `Invalid credentials` для неверного логина и пароля — перечисление пользователей невозможно.
- Пароли хешируются bcrypt с 12 раундами. Политика пароля одна для регистрации и для создания пользователя админом.
- Роль проверяется по БД при каждом запросе; деактивированный пользователь не получает доступ.

## Принятые риски

1. **`braces` в инструментах сборки (7 high, dev).** Исправления нет. Уязвимость — DoS при обработке шаблонов glob. Шаблоны задаёт только наш код, пользовательского ввода они не содержат. Продакшен-зависимости чистые, CI проверяет их (`npm audit --omit=dev`). Устранить можно заменой `tsc-alias` и `nodemon` на инструменты без `chokidar` 3 — отдельная задача.
2. **JWT в `localStorage`.** Смягчено CSP и линтером. Полное решение — httpOnly-cookie с `SameSite` и CSRF-защитой. Это изменение затрагивает фронтенд и API, поэтому оно вынесено отдельно.
3. **Выход не отзывает токен; срок 24 часа.** Деактивация пользователя действует сразу (роль читается из БД), но уже выданный токен действует до истечения срока. Для отзыва нужен список отозванных токенов или короче срок (`JWT_EXPIRES_IN`).
4. **Rate limit хранится в памяти процесса.** На Vercel у каждого экземпляра свой счётчик. Полная защита требует общего хранилища (Redis).
5. **Пароли в истории git.** Тестовые пароли (`Admin123456` и др.) остаются в старых коммитах. Переписывать историю не стали: защиту даёт смена паролей в БД, а не скрытие в истории.
6. **`trust proxy = 1`** верно только при одном прокси перед приложением (Vercel или nginx). Если приложение открыть напрямую, клиент может подменить адрес через `X-Forwarded-For`.

## Требует действия

1. **Продакшен-БД.** Проверить список пользователей (`select username, role, is_active from users;`) и сменить пароли всех четырёх учёток: из `backend/` с `DB_*`, указывающими на продакшен, и переменными `ADMIN_PASSWORD`, `MANAGER_PASSWORD`, `ANALYST_PASSWORD`, `VIEWER_PASSWORD` выполнить `npx ts-node src/database/update-passwords.ts`. Нужен рабочий `DB_PASSWORD` в Vercel: сейчас вход в БД падает с `password authentication failed`.
2. **Роль БД (пункт 13).** Проверить `select rolname, rolbypassrls from pg_roles where rolname = 'postgres';`. Если `BYPASSRLS = true`, перевести backend на роль приложения без этого флага.
3. **Docker-compose (пункт 12).** Убрать значения по умолчанию для паролей и не публиковать порты БД, Redis и служебных сервисов на хост.
4. **Проверить CSP в браузере.** Заголовки проверены сборкой, но не в живом приложении: если какой-то экран использует запрещённый ресурс, в консоли браузера появится ошибка CSP. Исправляется добавлением разрешённого источника в `vercel.json`.
5. **Решить по пункту 2 («Принятые риски»)**: переход на httpOnly-cookie.

## Как проверить

```bash
# Зависимости (продакшен) — как в CI
cd backend && npm ci && npm audit --omit=dev --audit-level=high
cd frontend && npm ci && npm audit --omit=dev --audit-level=high

# Полный аудит (включая dev)
cd backend && npm audit
cd frontend && npm audit

# Статический анализ — как в CI
semgrep scan --config p/owasp-top-ten --config p/nodejs --config p/javascript --config p/typescript --metrics=off --error --severity ERROR backend/src frontend/src

# Тесты и сборка
cd backend && npm run lint && npm run type-check && npm run test:unit && npm run build
cd frontend && npm run lint && npx vitest run && npm run build
```

## Что не проверено

- Работа приложения под CSP в браузере (см. «Требует действия», пункт 4).
- Загрузка CSV с новыми лимитами на реальных файлах и на продакшене.
- Ограничение входа через прокси Vercel (проверено только локально с `X-Forwarded-For`).
- Роль БД и продакшен-пользователи — нет доступа к базе.
