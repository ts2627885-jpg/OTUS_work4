# Журнал рефакторинга и отладки АЗС-Пульт

Полные тексты запросов — в [PROMPTS.md](PROMPTS.md), формулы правил — в [RULES_FORMULAS.md](RULES_FORMULAS.md).

Документ описывает, как велась работа с ИИ-агентом (Claude Code): какие запросы ставились, какие проблемы
возникали, как их решали, и какие приёмы дали лучший результат. Состояние кода — на 12.10.2026.

---

## 1. Какие запросы использовались

Запросы формулировались задачами по шагам. Ниже — ключевые по смыслу (в исходной речи — на русском).

| Этап | Запрос (кратко) | Что получили |
|---|---|---|
| Данные | «проверь кодировку файлов в папке backup» | Анализ UTF-8/BOM/окончаний строк по всем CSV |

| Данные | «замени названия АЗС / значения продаж синтетическими» | Замены в копиях и оригиналах, проверка счётчиков |
| БД | «удали старые данные и загрузи новые из папки» | Пересборка схемы `azs` пайплайном, резервные копии |
| Синхронизация | «в пульте должны подтягиваться новые АЗС автоматически» | `sync_public.sql` и шаг 4b пайплайна |
| Функции | «рекомендации и информация по новым АЗС — автоматически» | Скрипт пересчёта и шаг 4c |
| Интерфейс | «кнопка: сформировать рекомендации и проверку АЗС» | `GET /api/stations/check` и кнопка «Проверить АЗС» |
| Загрузка | «при загрузке CSV всё обновляется» | Поддержка `stations.csv`, синхронизация после загрузки |
| Моки | «использовать моки для проверки отображения» | Фикстуры из реальных ответов API, адаптер axios |
| Тесты | «создать тесты (позитивные и ошибки), исправить баги» | Jest и Vitest, найденные баги и исправления |
| Адаптивность | «проверить на разных экранах, медиа-запросы, таблицы карточками» | `responsive.css`, `tableLabels.js`, снимки Chrome |
| Рефакторинг | «улучшить структуру, производительность, читаемость, задокументировать» | Этот документ и правки ниже |

проходить», «покажи на 375 px»). Размытые запросы («сделай красиво») агент сначала уточнял или сводил к проверяемым
пунктам.

## 2. Проблемы и способы решения

### 2.1 Данные и кодировки
- **Иероглифы в Excel.** UTF-8 без BOM Excel открывает как cp1251. Решение: копии файлов с BOM (`_excel/`), без
  изменения исходников.
- **Невидимый BOM в заголовке.** Заголовок `﻿Дата` не совпадает с `Дата`. Учтено в загрузчиках (`utf-8-sig`).

### 2.2 База и схемы
- **Пайплайн не видел промо-колонку.** В `promotions.csv` нет колонки «Срок действия». Решение: колонка стала
  необязательной в `clean_promotions.py`.
- **Новая станция без продаж падала на синхронизации.** `fuel_types` стал NULL. Решение: `COALESCE(..., '{}')`.
- **Регистрация возвращала 500.** Код писал в `role_id`, а в таблице роль текстом. Решение: запись в `role`.
  Нашли тестом — это главный пример пользы тестов для поиска скрытых расхождений схемы и кода.

### 2.3 Логи и конфиги
- **`[object Object] 200` в логах.** `requestLogger` передавал объект запроса туда, где ждали строку. Исправлено
  сигнатурой вызова.
- **Прокси Vite указывал на Docker-хост `backend:3000`.** Исправлено на `localhost:3001` с переопределением через
  переменную окружения.
- **28 ошибок `tsc`.** Часть — расхождение типов со схемой БД, часть — неверные типы параметров логгера. Типы
  приведены к реальным данным, `tsc` стал чистым.

### 2.4 Тесты
- **Тесты зависели друг от друга.** Повторная регистрация одного логина в `beforeEach` давала 409. Решение:
  очистка тестовых пользователей после каждого теста.
- **Тест обновления токена был недетерминированным.** JWT с `iat` в секундах совпадал со старым токеном. Решение:
  пауза 1,1 с (или сравнение по времени выдачи).
- **Мок-конфиг Jest не знал `@controllers`.** Добавлен маппинг путей.
- **Установка `jsdom` зависала** (реестр npm временно недоступен из окружения). Сначала тесты шли в среде `node`
  (логика store и мок-адаптера). Когда реестр ответил, `jsdom@24` установлен, среда переключена на `jsdom`, добавлены
  тесты компонента `RecommendationsView`.

### 2.5 Адаптивность
- **Снимки Chrome при 375 px обрезались.** Headless Chrome не уменьшает окно ниже ~500 px. Решение: проверка через
  iframe шириной 375 px и измерение `scrollWidth`/`getBoundingClientRect`.
- **Таблицы на телефоне.** Решение: подписи из заголовков `<th>` через `data-label` и CSS-карточки.

### 2.6 Производительность
- **`/api/analysis/rules` — 6–7 с.** Замеры показали: эластичность (21 мс) не была узким местом, основное время
  съедал запрос конкурентов в `compElasticityRows`: коррелированные подзапросы по каждой строке продаж. Решение:
  соединение с агрегатом по диапазону дат. Время сократилось до ~0,3–0,5 с (см. таблицу в разделе 4).
- **Параметризованный запрос медленнее литерального.** Один и тот же SQL с литералом давал 115 мс, с параметром
  `$1` — 5,8 с (план общего вида). Решение: переписывание запроса, которое устойчиво к параметрам.
- **Повторные вызовы регрессии.** Одна страница вызывает эластичность десятки раз. Решение: кэш оценок, привязанный
  к версии данных (дата и число строк `azs.fuel_daily`), чтобы не отдавать устаревшие результаты после загрузки.

### 2.7 Структура кода
- **Одна и та же проверка роли в трёх файлах** (с разным SQL и разными сообщениями). Решение: общий middleware
  `requireRole` в `backend/src/middleware/roles.middleware.ts` и общий `UUID_RE` в `backend/src/utils/uuid.ts`.
- **Дублирование `UUID_RE`** в трёх маршрутах. Вынесено в `utils/uuid.ts`.

## 3. Какие техники оказались наиболее эффективными

1. **Измерять, а не угадывать.** Замеры `curl` по эндпоинтам и таймеры внутри сервисов сразу показали, что тормозит
   не эластичность (как предполагалось сначала), а запрос конкурентов. Без замеров кэш эластичности оказался бы
   ненужным.
2. **Сравнивать результаты до и после.** Для SQL-перепиской проверяли равенство агрегатов (количество строк и суммы
   `comp`, `comp_lag`) между старым и новым запросом. Совпало точно (375 296,9596 и 374 533,9706).
3. **Тесты, которые ловят расхождения схемы.** Один интеграционный тест нашёл, что код пишет в колонку, которой нет в
   БД. Юнит-тесты на заглушках этого не показывают.
4. **Проверка через реальный браузер и измерения размеров.** Headless Chrome и iframe нужной ширины дали проверяемые
   снимки; `scrollWidth` и `getBoundingClientRect` показали, где именно выходит за экран.
5. **Фикстуры из реальных ответов API.** Моки, снятые с работающего backend, сохраняют форму ответов и не
   расходятся с кодом, в отличие от вручную написанных.
6. **Небольшие проверяемые шаги.** Каждое изменение сопровождалось `tsc`, тестами и проверкой эндпоинтов по ролям.
   Это позволяло быстро локализовать регрессию.
7. **Поиск дубликатов по коду.** Просмотр всех мест с одинаковым SQL и проверками (`SELECT role FROM users`) дал
   основу для вынесения общего middleware.

## 5. Статус после доработки

Закрыто:
- **Тесты backend (43):** роли (`requireRole`: позитивные и 403, неверный id, нет пользователя, сбой БД), синхронизация
  `public` (новые и удалённые АЗС, откат транзакции при ошибке), определение типов CSV, auth.
- **Тесты frontend (21):** store входа, мок-адаптер, `RecommendationsView` (3), `AzsListView` (2),
  `AzsDetailView` (5: паспорт, редактирование менеджером, ошибка сохранения, скрытая кнопка для аналитика, 404), `AnalyticsView` (4).
- **Адаптивность:** длинные значения в карточках выравниваются по левому краю.
- **Фикстуры моков:** `frontend/scripts/refresh-mock-fixtures.mjs` обновляет снимок с работающего backend.
- **Пересчёт рекомендаций по расписанию:** `scripts/schedule-recommendations.ps1`.
  Скрипт создаёт задание в Планировщике Windows (03:00 ежедневно). Он не запускался: это изменение системы, его нужно
  выполнить вручную от администратора.

Не закрыто:
- Тесты экранов админки и импорта: не написаны.
- Синхронизация `public` перезаписывает станции, созданные вручную в приложении. Нужно решение: запретить ручное
  создание или сохранять такие станции при синхронизации.
- Проверка на настоящем телефоне или эмуляторе с сенсорным вводом не выполнялась.

Сверка с `docs/Error_Scenarios_Matrix.md`:
- Реализованы и проверены тестами: неверный пароль (401), нет прав (403), повтор логина (409), неверные данные (400),
  неизвестный тип CSV (400), откат транзакции при ошибке импорта и синхронизации.
- В матрице, но не реализованы: повторные попытки с экспоненциальной задержкой, опрос долгих операций, офлайн-кэш.
  Для учебного проекта их можно считать запланированными.
