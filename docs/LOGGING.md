# Логирование

В проекте четыре места, где фиксируются события. Они отвечают на разные вопросы и живут в разных местах.

| Что | Где хранится | Кто читает | Зачем |
|---|---|---|---|
| Журнал приложения (INFO, WARN, ERROR, DEBUG) | stdout функции Vercel; файлы `logs/app-ГГГГ-ММ-ДД.log` (локально) | разработчик через `vercel logs` | что делал сервер, почему упал запрос |
| Предупреждения и ошибки | таблица `app_logs` (при `LOG_TO_DB=true`) | admin через SQL | история сбоев, которую не теряет Vercel |
| Входы в систему | таблица `login_logs` | admin | кто и когда входил, неудачные попытки |
| Действия пользователей | таблица `audit_logs` | admin | кто что изменил: станции, цены, пользователи |

## Журнал приложения

Модуль `backend/src/utils/logger.ts`. Уровни: `debug`, `info`, `warn`, `error`. Формат: в локальной разработке — читаемые строки, в продакшене — JSON в одну строку (`timestamp`, `level`, `message`, `context`, `data`).

Файлы пишутся локально в `logs/` (каталог меняется `LOG_DIR`). Файл создаётся на каждый день, при превышении `LOG_MAX_MB` (по умолчанию 20) открывается следующий, файлы старше `LOG_RETENTION_DAYS` (по умолчанию 90) удаляются.

На Vercel файловая система временная, файлы не сохраняются. Записи доступны через `vercel logs` и Dashboard → Logs. На плане Hobby логи хранятся около часа, поэтому важные сбои переносите в `app_logs`.

Просмотр логов функции:
```bash
vercel logs --deployment <адрес деплоя> --query 'level:error'
vercel logs --deployment <адрес деплоя> --query 'Database'
```

## Таблица `app_logs`

Включается переменной `LOG_TO_DB=true` (в продакшене включена). Пишутся только `warn` и `error`, без пользовательского контекста. Миграция `015_app_logs.sql`.

Колонки: `id`, `created_at`, `level` (`warn` или `error`), `context`, `message`, `data` (JSON), `error_name`, `error_message`.

Просмотр последних ошибок (SQL Editor, роль `postgres`):
```sql
select created_at, level, context, message, error_message
from app_logs
order by created_at desc
limit 50;
```

Записи попадают в таблицу фоново, поэтому сбой записи не мешает ответу пользователю. Политика RLS: вставка разрешена всем контекстам, чтение — только admin.

## Журнал входов `login_logs`

Пишется для каждой попытки входа через `POST /api/auth/login`: логин, результат (`success` или `failure`), адрес клиента (`req.ip` при `trust proxy = 1`), браузер, id пользователя при успехе. Логин ограничен 100 символами, браузер — 500.

Неудачные попытки видны здесь же, если нужно расследовать перебор паролей.

## Журнал действий `audit_logs`

Пишется функцией `audit()` в `services/access.service.ts`: кто (`user_id`, `actor_name`), действие (`action`), объект (`entity_type`, `entity_id`), изменения (JSON), адрес клиента. Журнал не прерывает операцию: если запись не удалась, действие всё равно выполняется.

Просмотр в интерфейсе: раздел «Администрация» → журналы. Прямой SQL:
```sql
select created_at, actor_name, action, entity_type, entity_id
from audit_logs
order by created_at desc
limit 100;
```

## Что не записывается

- Пароли, токены, Client Secret и ключи API — не пишутся ни в один журнал.
- Почта пользователя в журнале регистрации не пишется, только логин (после исправления из аудита).
- Тело запросов в журнал приложения не попадает.

## Алерты

Журналы сами алерты не отправляют. Внешний мониторинг (UptimeRobot) проверяет доступность и готовность сервиса — см. [MONITORING.md](MONITORING.md).
