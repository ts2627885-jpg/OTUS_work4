## 🎯 Обзор системы

### Цель
Создать enterprise-ready систему управления ценовой политикой для автомобильных заправочных станций (АЗС) с поддержкой аутентификации, контролем доступа, хранением данных в PostgreSQL и развёртыванием через Docker.

### Основные задачи
- 📊 Анализ данных о продажах, трафике, ценах конкурентов
- 💰 Генерация рекомендаций по оптимизации ценообразования
- 🔐 Безопасная аутентификация и авторизация пользователей
- 📈 Отслеживание метрик эффективности АЗС
- 🚀 Масштабируемое развёртывание в Docker

### Целевая аудитория
- **Администраторы** — управление системой, пользователями, настройками
- **Менеджеры АЗС** — просмотр рекомендаций, анализ своих станций
- **Аналитики** — анализ данных, сравнение АЗС, выявление трендов
- **Просмотрщики** — доступ только для чтения

## ✅ Функциональные требования

### FR-1: Аутентификация и авторизация

#### FR-1.1 Регистрация пользователя
- **Требование:** Система должна позволять регистрироваться через форму входа
- **Входные данные:** username (мин. 3 символа), email (валидный формат), пароль (мин. 6 символов)
- **Выход:** Аккаунт создан, пользователь активирован по умолчанию
- **Роль:** Все пользователи регистрируются с ролью "Viewer"
- **Валидация:** Email должен быть уникален, username должен быть уникален
- **Ошибки:** Сообщение об ошибке если пользователь уже существует

#### FR-1.2 Вход в систему
- **Требование:** Пользователь может войти с username/email и паролем
- **Механизм:** JWT токен с временем жизни 24 часа
- **Хранение:** Токен в localStorage браузера
- **Автообновление:** Если токен истёк, перенаправить на страницу входа
- **Логирование:** Записать IP, User-Agent, время входа, статус (успех/ошибка)

#### FR-1.3 Выход из системы
- **Требование:** Пользователь может выйти из системы
- **Результат:** Токен удалён из localStorage, редирект на страницу входа
- **Сессия:** Очистить данные сессии на сервере (если используются)

### FR-2: Управление ролями и правами

#### FR-2.1 Роли в системе
Система поддерживает 4 встроенные роли:

**Admin** — полный доступ
- ✅ Просмотр всех АЗС
- ✅ Редактирование АЗС
- ✅ Просмотр рекомендаций
- ✅ Отметить рекомендацию выполненной
- ✅ Загрузка CSV файлов
- ✅ Управление пользователями и ролями
- ✅ Изменение настроек системы
- ✅ Просмотр логов и аудита

**Manager** — управление своими АЗС
- ✅ Просмотр только своих АЗС (назначены менеджеру)
- ✅ Редактирование своих АЗС
- ✅ Просмотр рекомендаций для своих АЗС
- ✅ Отметить рекомендацию выполненной
- ❌ Загрузка CSV
- ❌ Управление пользователями
- ❌ Изменение настроек системы

**Analyst** — анализ данных
- ✅ Просмотр всех АЗС
- ✅ Просмотр рекомендаций
- ✅ Анализ и сравнение АЗС
- ❌ Редактирование АЗС
- ❌ Отметить рекомендацию
- ❌ Загрузка CSV
- ❌ Управление пользователями

**Viewer** — только чтение
- ✅ Просмотр всех АЗС
- ✅ Просмотр рекомендаций
- ❌ Редактирование чего-либо
- ❌ Загрузка CSV
- ❌ Управление пользователями

#### FR-2.2 Granular Access Control
- **Требование:** Менеджеры видят только АЗС, назначенные им
- **Механизм:** Таблица `azs_access` в БД
- **Администратор может:**
  - Назначить менеджера на АЗС
  - Передать АЗС другому менеджеру
  - Отозвать доступ менеджера к АЗС

#### FR-2.3 Проверка прав на уровне API
- **Требование:** Каждый endpoint проверяет права пользователя
- **Механизм:** Middleware RBAC перед обработкой запроса
- **Ошибка:** 403 Forbidden если права недостаточно

### FR-3: Управление АЗС

#### FR-3.1 Просмотр АЗС
- **Требование:** Список всех доступных пользователю АЗС
- **Поля:** ID, название, город, регион, менеджер, дата создания
- **Фильтрация:** По городу, регионам, менеджеру
- **Сортировка:** По названию, городу, рейтингу

#### FR-3.2 Просмотр деталей АЗС
- **Требование:** Подробная информация об АЗС
- **Включает:**
  - Базовая информация (название, адрес, менеджер)
  - Ежедневные продажи топлива (таблица + график)
  - Трафик (таблица + график)
  - Цены конкурентов (таблица + график)
  - Погода (таблица)
  - Рекомендации (список по приоритету)
  - Метрики эффективности (рейтинг, KPI)

#### FR-3.3 Редактирование АЗС (для Admin и Manager)
- **Требование:** Изменение базовой информации АЗС
- **Поля:** название, адрес, город, регион
- **Валидация:** Обязательные поля заполнены
- **Логирование:** Записать кто и когда изменил АЗС

### FR-4: Анализ данных и рекомендации

#### FR-4.1 Загрузка CSV файлов
- **Требование:** Admin может загружать CSV файлы с данными
- **Типы файлов:**
  - `fuel_sales.csv` — продажи топлива
  - `traffic.csv` — данные о трафике
  - `weather.csv` — погода
  - `competitor_prices.csv` — цены конкурентов
  - `accompanying_products.csv` — сопутствующие товары

#### FR-4.2 Валидация и импорт данных
- **Требование:** CSV парсится, валидируется, загружается в БД
- **Проверки:**
  - Формат данных соответствует ожиданиям
  - Даты в правильном формате (YYYY-MM-DD)
  - Числовые значения корректны
  - Внешние ключи существуют
- **Результат:** Если ошибки — показать какие строки не загружены
- **Транзакция:** Либо всё загружается, либо ничего (atomicity)

#### FR-4.3 Генерация рекомендаций
- **Требование:** На основе загруженных данных генерируются рекомендации
- **Типы рекомендаций:**
  - Ценовая политика (PRICE-001…PRICE-005)
  - Управление трафиком (TRAFFIC-001…TRAFFIC-003)
  - Промо-акции (PROMO-001…PROMO-003)
  - Сопутствующие товары (SHOP-001…SHOP-004)
- **Расчёты:** Каждая рекомендация содержит формулу расчёта эффекта
- **Приоритет:** Urgent, High, Medium, Low
- **Статус:** Active, Completed, Ignored

#### FR-4.4 Просмотр рекомендаций
- **Требование:** Пользователь видит рекомендации для своих АЗС
- **Отображение:**
  - Таблица с фильтрами (АЗС, категория, приоритет, статус)
  - Описание и обоснование
  - Формула расчёта эффекта
  - Потенциальный эффект в ₽/сут и %
  - Кнопка "Выполнено" (для Manager)
- **Архив:** Завершённые рекомендации хранятся в архиве

#### FR-4.5 Отметить рекомендацию как выполненную
- **Требование:** Manager может отметить рекомендацию как выполненную
- **Данные:** Сохранить who (user_id), when (timestamp)
- **Статус:** Изменить с "active" на "completed"
- **История:** Остаётся в БД для аудита

### FR-5: Пульт управления

#### FR-5.1 Главная страница (Dashboard)
- **Требование:** При входе пользователь видит главный пульт
- **Содержание:**
  - Рейтинг АЗС (таблица с 7 показателями)
  - Карточки каждой АЗС (объём, цены, позиция)
  - Срочные рекомендации (топ 5)
  - Метрики по выбранному окну анализа (7, 14, 28, 56, 91 дней)
- **Управление:** Выбор дня анализа, окна, фильтр АЗС
- **Динамика:** Все элементы обновляются при смене фильтров

#### FR-5.2 Вкладка «Ценовая политика»
- **Требование:** Анализ цен и чувствительности объёма к цене
- **Содержит:**
  - Таблица текущих цен по видам топлива
  - График объёма за период (7-дневное скользящее среднее)
  - Таблица эластичности (% объёма при ±1 ₽)
  - Симулятор: ввести цену → прогноз эффекта

#### FR-5.3 Вкладка «Конкуренты»
- **Требование:** Мониторинг цен конкурентов
- **Содержит:**
  - Таблица конкурентов (цена, изменение за 7 дней, разница с вами)
  - График за 120 дней для каждого вида топлива
  - Таблица эластичности (как меняется ваш объём при смене цены конкурента)
  - Рекомендации по реакции на движения конкурентов

#### FR-5.4 Вкладка «Трафик»
- **Требование:** Анализ потока машин
- **Содержит:**
  - Таблица структуры потока (грузовые, легковые)
  - Доля заезда (л/ТС) для каждой АЗС
  - График доли заезда (общий и по АЗС)
  - Таблица эластичности трафика (% объёма при +10% ТС)

#### FR-5.5 Вкладка «Факторы спроса»
- **Требование:** Анализ влияния внешних факторов
- **Факторы:**
  - День недели (пн-вс, эффект на объём)
  - Праздники и выходные
  - Погода (температура, осадки, явления)
  - Сезонность (по месяцам)
- **Отображение:** Таблицы с доверительными интервалами
- **Данных недостаточно:** Показать сообщение вместо графика

#### FR-5.6 Вкладка «Влияние на объём»
- **Требование:** Интегрированный анализ факторов
- **Разделы:**
  - Трафик (главный фактор) — эластичность
  - Цена — эластичность, эффект конкурентов
  - День недели — таблица эффектов
  - Сезонность — таблица месячных эффектов
  - Погода — коэффициенты влияния
  - Сетевые эффекты — сравнение с сетью
  - Рекомендации по росту

#### FR-5.7 Вкладка «Сопутствующие товары»
- **Требование:** Анализ магазина
- **Содержит:**
  - Сводка выручки магазина, маржа
  - Структура по категориям (таблица + график)
  - АЗС × категория — выручка на 1000л, отклонение от медианы
  - Динамика за 12 месяцев
  - Факторы спроса (топливо, температура, праздники)
  - Ценовая политика по категориям
  - Симулятор цены категории

#### FR-5.8 Вкладка «Акции»
- **Требование:** Управление и анализ промо-акций
- **Содержит:**
  - Календарь акций (когда, на что)
  - Таблица эффектов с доверительными интервалами
  - Таблица мер (скидки, товары, результаты)

#### FR-5.9 Вкладка «Данные»
- **Требование:** Информация об источниках данных
- **Содержит:**
  - Источник файлов (откуда загружены)
  - Период данных (от–до)
  - Какие данные загружены (галочки)
  - Требования к формату файлов
  - История импортов (дата, строк, статус)

#### FR-5.10 Вкладка «Администрирование» (для Admin)
- **Требование:** Управление пользователями и настройками
- **Пользователи:**
  - Список всех пользователей (username, email, роль, дата создания, статус)
  - Поиск по username/email
  - Изменение роли пользователя
  - Блокировка/разблокировка пользователя
  - Удаление пользователя
  - Назначение менеджеров на АЗС
- **Настройки:**
  - Загрузка/скачивание config.json
  - Изменение параметров (маржи, пороги, веса рейтинга)
  - Просмотр истории изменений
- **Аудит:**
  - Логи входов (кто, когда, IP, статус)
  - История изменений рекомендаций
  - История импортов данных

### FR-6: Интеграция данных

#### FR-6.1 REST API
- **Требование:** Все функции доступны через REST API
- **Формат:** JSON
- **Аутентификация:** Bearer token (JWT)
- **Версионирование:** /api/v1/...

#### FR-6.2 Эндпоинты API
```
POST   /api/auth/register           — Регистрация
POST   /api/auth/login              — Вход
GET    /api/azs                     — Список АЗС
GET    /api/azs/:id/data            — Данные АЗС
GET    /api/azs/:id/recommendations — Рекомендации
POST   /api/recommendations/:id/complete — Отметить выполненной
POST   /api/admin/import            — Загрузить CSV
GET    /api/admin/users             — Список пользователей
POST   /api/admin/users             — Создать пользователя
PUT    /api/admin/users/:id         — Изменить пользователя
DELETE /api/admin/users/:id         — Удалить пользователя
```

## ⚡ Нефункциональные требования

### NFR-1: Производительность

#### NFR-1.1 Время отклика API
- **Требование:** Эндпоинты должны отвечать быстро
- **Стандарты:**
  - GET запрос без фильтров: < 200ms
  - GET запрос с фильтрами: < 500ms
  - POST запрос: < 1000ms
  - Импорт CSV (50k строк): < 30 сек
- **Нагрузка:** Система должна обрабатывать 100 одновременных пользователей

#### NFR-1.2 Фронтенд производительность
- **Требование:** UI должен быть быстрым и отзывчивым
- **Стандарты:**
  - Загрузка страницы: < 2 сек
  - Смена фильтров: < 300ms
  - Отрисовка графиков: < 500ms
  - Первый экран: < 1 сек (First Contentful Paint)
- **Оптимизация:**
  - Кэширование на фронтенде (localStorage)
  - Ленивая загрузка графиков
  - Виртуализация таблиц (если много строк)

#### NFR-1.3 Масштабируемость БД
- **Требование:** БД должна быстро работать с растущим объёмом данных
- **Индексы:** На часто фильтруемых колонках (azs_id, date, fuel_type)
- **Партиционирование:** По датам (если таблица растёт выше 1GB)
- **Очистка:** Архивирование данных старше 2 лет

### NFR-2: Надёжность

#### NFR-2.1 Доступность
- **Требование:** Система должна быть доступна 99.5% времени
- **Включает:** Плановое техническое обслуживание 0.5%
- **SLA:** 99.5% uptime в месяц

#### NFR-2.2 Обработка ошибок
- **Требование:** Система корректно обрабатывает ошибки
- **Фронтенд:**
  - Показывать пользователю ясные сообщения об ошибках
  - Предложить повторить действие или перезагрузиться
  - Не показывать технические детали
- **Backend:**
  - Логировать все ошибки с context
  - Не раскрывать внутренние детали в API ответах
  - Graceful shutdown при критических ошибках

#### NFR-2.3 Восстановление после сбоя
- **Требование:** Система должна восстанавливаться после сбоя
- **БД:** Регулярные бэкапы (ежедневно)
- **Восстановление:** Возможность восстановить данные на момент времени (PITR)
- **Мониторинг:** Alerts если БД недоступна > 1 минуты

### NFR-3: Масштабируемость

#### NFR-3.1 Масштабирование по пользователям
- **Требование:** Система должна поддерживать рост пользователей
- **Текущее:** 100 активных пользователей
- **Целевое:** 1000+ пользователей
- **Механизм:** Горизонтальное масштабирование (несколько инстансов backend)

#### NFR-3.2 Масштабирование по данным
- **Требование:** Система должна работать с растущим объёмом данных
- **Текущее:** 50 АЗС × 2 года данных = 36 млн записей
- **Целевое:** 500 АЗС × 5 лет данных = 900 млн записей
- **Механизм:** Шардирование или партиционирование БД

#### NFR-3.3 Масштабирование по вычислениям
- **Требование:** Расчёты моделей должны масштабироваться
- **Текущее:** Расчёт за 240 сек для 50 АЗС
- **Целевое:** Расчёт за < 60 сек для 500 АЗС
- **Механизм:** Параллельный расчёт (Worker Threads)

### NFR-4: Удобство использования

#### NFR-4.1 Интерфейс
- **Требование:** UI должен быть интуитивным и удобным
- **Принципы:**
  - Минималистичный дизайн
  - Тёмная и светлая темы
  - Адаптивность для мобильных устройств
  - Поддержка русского языка
- **Тестирование:** Юзабилити-тесты с реальными пользователями

#### NFR-4.2 Справка и документация
- **Требование:** Пользователи должны понимать систему
- **Включает:**
  - Всплывающие подсказки на сложных местах
  - Встроенная справка (Help)
  - Видео-туториалы
  - Документация на русском

#### NFR-4.3 Локализация
- **Требование:** Система работает на русском языке
- **Включает:**
  - Все тексты на русском
  - Форматы дат/чисел по стандартам РФ
  - Валюта ₽ (рубли)
  - Часовой пояс по регионам России

### NFR-5: Поддерживаемость

#### NFR-5.1 Код и архитектура
- **Требование:** Код должен быть чистым и понятным
- **Стандарты:**
  - ESLint конфигурация (для JavaScript)
  - Код ревью перед merge в main
  - Комментарии для сложной логики
  - Модульная архитектура

## 🔒 Требования к безопасности

### SEC-1: Аутентификация

#### SEC-1.1 Хеширование паролей
- **Требование:** Пароли никогда не хранятся в открытом виде
- **Алгоритм:** bcrypt с salt (минимум 10 раундов)
- **Проверка:** Сравнение хешей, а не паролей

#### SEC-1.2 JWT токены
- **Требование:** Безопасная выдача и проверка токенов
- **Срок действия:** 24 часа
- **Подпись:** HS256 с сильным SECRET
- **Хранение:** localStorage в браузере (или httpOnly cookies)
- **Refresh:** Механизм обновления токена без повторного входа

#### SEC-1.3 Защита от brute force
- **Требование:** Защита от попыток подбора пароля
- **Механизм:** Ограничение попыток входа (максимум 5 за 15 минут)
- **Результат:** Блокировка аккаунта на 15 минут после 5 ошибок

### SEC-2: Авторизация

#### SEC-2.1 Role-Based Access Control (RBAC)
- **Требование:** Каждый пользователь видит только то, что ему доступно
- **Проверка:** На каждом эндпоинте API
- **Уровни:** Role + Entity-level (АЗС)

#### SEC-2.2 Granular Access
- **Требование:** Менеджеры видят только свои АЗС
- **Механизм:** Таблица azs_access с правами
- **Проверка:** При выборе АЗС проверить что пользователь имеет доступ

### SEC-3: Защита данных

#### SEC-3.1 Шифрование в пути
- **Требование:** Данные в пути должны быть защищены
- **Механизм:** HTTPS (TLS 1.2+)
- **Сертификаты:** Действующие сертификаты от trusted CA

#### SEC-3.2 Шифрование в покое
- **Требование:** Чувствительные данные в БД должны быть зашифрованы
- **Данные:** Пароли (bcrypt), пароли API (AES-256)
- **Ключи:** Хранить отдельно от кода (environment variables)

#### SEC-3.3 SQL Injection защита
- **Требование:** Система защищена от SQL-injection
- **Механизм:** Параметризованные запросы (prepared statements)
- **Библиотеки:** pg использует параметризацию

#### SEC-3.4 XSS защита
- **Требование:** Система защищена от XSS атак
- **Механизм:** Vue.js автоматически экранирует HTML
- **Дополнительно:** Content Security Policy (CSP) заголовки

#### SEC-3.5 CSRF защита
- **Требование:** Система защищена от CSRF
- **Механизм:** CSRF токены для POST/PUT/DELETE запросов
- **Альтернатива:** SameSite cookies

### SEC-4: Аудит и мониторинг

#### SEC-4.1 Логирование действий
- **Требование:** Все значимые действия логируются
- **Включает:**
  - Вход/выход пользователей
  - Изменение ролей
  - Загрузка данных
  - Изменение рекомендаций
  - Доступ к чувствительным данным
- **Хранение:** Минимум 90 дней (или 1 год для критических)
- **Неизменяемость:** Логи не должны удаляться, только архивироваться

#### SEC-4.2 Мониторинг безопасности
- **Требование:** Отслеживать попытки атак
- **Включает:**
  - Множественные failed login attempts
  - Аномальная активность (много запросов за короткое время)
  - Попытки доступа без прав
  - Изменения конфигурации
- **Alerts:** Мгновенные alerts в Slack если что-то подозрительное

#### SEC-4.3 Инцидент-менеджмент
- **Требование:** Процесс реагирования на инциденты
- **План:** Процедура обнаружения, анализа, реагирования
- **Коммуникация:** Как информировать пользователей о проблемах

### SEC-5: Управление доступом

#### SEC-5.1 Управление ключами
- **Требование:** JWT_SECRET, DB_PASSWORD в production должны быть сильными
- **Требования:**
  - Минимум 32 символа
  - Комбинация букв, цифр, спецсимволов
  - Никогда не коммитить в git
  - Использовать environment variables или Vault

#### SEC-5.2 Управление доступом к коду
- **Требование:** Код репозитория должен быть защищен
- **Правила:**
  - Только авторизованные разработчики имеют доступ
  - Code review перед merge
  - Защита branch main от direct pushes
