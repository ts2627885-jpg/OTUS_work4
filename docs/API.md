# API АЗС-Пульт

Собственный REST API на Express (`backend/src`), база — Supabase PostgreSQL. Базовый адрес: `http://<host>:3001/api` (в проекте фронтенд проксирует `/api`).

## Почему свой API, а не Supabase REST

Supabase генерирует REST API (PostgREST) из таблиц автоматически. Для этого проекта он не подходит:

- **Другая аутентификация.** Пользователи и JWT — свои (таблица `users`, токен из `auth.service`). PostgREST ждёт JWT Supabase Auth, поэтому пришлось бы переводить учётные записи.
- **Бизнес-правила не выполняются.** Проверка прав по станциям, аудит (`audit_logs`), валидация входных данных, пересчёт рекомендаций — всё это в сервисах Express. PostgREST дал бы прямой доступ к таблицам мимо них.
- **Уже есть защита на уровне базы.** RLS (миграция 010, 012) работает через контекст, который ставит бэкенд. Открывать таблицы через PostgREST значило бы ставить второй путь доступа к тем же данным.

Supabase REST при этом отключён для ролей `anon` и `authenticated` (миграция 011), поэтому публичный ключ к данным не открывает.

## Аутентификация

- `POST /api/auth/login` — `{ "username", "password" }` → `data.token.access_token`.
- Остальные запросы: заголовок `Authorization: Bearer <access_token>`.
- Нет токена или он неверный → `401 { "success": false, "error": "...", "code": "AUTHENTICATION_ERROR" }`.

## Роли

| Роль | Станции | Рекомендации | Планы теста цен | Пользователи |
|---|---|---|---|---|
| admin | все, полный CRUD | все, пересчёт, закрытие | все, создание черновика | полный CRUD |
| manager | только назначенные (`azs_access`), изменение | по своим станциям; сети — читает | по своим станциям, только чтение | нет |
| analyst | все, только чтение | все, только чтение | все, только чтение | нет |
| viewer | все, только чтение | все, только чтение | все, только чтение | нет |

Доступ проверяется дважды: в коде (`access.service.ts`, `requireRole`) и в базе (RLS). Если в коде ошибка, база всё равно не отдаст лишние строки.

## Формат ответов

Успех: `{ "success": true, "data": ... }` (для удаления — `{ "success": true, "message": "..." }`).

Ошибка: `{ "success": false, "error": "текст", "code": "..." }`. Коды HTTP:

| Код | Когда |
|---|---|
| 400 | неверные входные данные |
| 401 | нет или неверный токен |
| 403 | роль не позволяет операцию |
| 404 | ресурс не найден (в том числе станция, к которой нет доступа) |
| 409 | удаление невозможно: есть связанные данные |
| 500 | внутренняя ошибка (детали в логе, клиенту не отдаются) |

## Станции (CRUD)

### `GET /api/azs` — список
Доступ: все роли (manager — только назначенные).
Ответ: `data: [Station]`.

### `GET /api/azs/:id` — одна станция
Доступ: все роли с доступом к станции. Иначе `404`.

### `POST /api/azs` — создать
Доступ: admin. Тело:
```json
{ "name": "АЗС 130", "address": "...", "region": "...", "fuelTypes": ["A92", "DT"], "manager": "Иванов", "status": "active", "latitude": 56.8, "longitude": 35.9 }
```
- `name` обязательно, не короче 2 символов → иначе `400`.
- Ответ `201`, `data: Station`. Действие пишется в аудит (`station.create`).

### `PUT /api/azs/:id` — изменить
Доступ: admin; manager — если станция назначена. Передаются только изменяемые поля, остальные не трогаются (`COALESCE`).
Ответ `200`, `data: Station`. Неизвестная станция → `404`.

### `DELETE /api/azs/:id` — удалить
Доступ: admin.
- Ответ `200`, `{ "success": true, "message": "Deleted successfully" }`.
- Если у станции есть цены или продажи → `409`, станция остаётся.

### Формат станции
```json
{ "id": "uuid", "name": "АЗС 125", "address": "...", "region": "...", "fuelTypes": ["A92"], "manager": null, "status": "active", "latitude": null, "longitude": null }
```

## Тестирование

- Чтение: `curl -H "Authorization: Bearer $TOKEN" http://localhost:3001/api/azs` — ожидается `200`.
- Проверка прав: запрос `POST /api/azs` от viewer → `403`; от manager → `403`.
- Тест CRUD на станции: `node scripts/api-crud-check.mjs` (создаёт тестовую станцию, меняет, удаляет; запускать только по согласованию, это запись в базу).
- Полный набор по всем эндпоинтам и ролям: `node scripts/api-test.mjs`. Записи — `node scripts/api-write-test.mjs` (только тестовый бэкенд на 3005).

## Ответы сервера: ключевые детали

- Вход: `data.token.access_token`, `token_type`, `expires_in`; `data.user` содержит `id`, `username`, `email`, `role`, `permissions`, `azs_access`.
- Импорт CSV отвечает `200` с результатом по каждому файлу. Неизвестный формат — `ok:false` у файла, не ошибка запроса.

## Безопасность

- Пароли тестовых учётных записей (`admin`, `manager`, `analyst`, `viewer`) лежат в отслеживаемых файлах репозитория (`LoginView.vue`, тесты, документация). Репозиторий доступен без авторизации. Те же пароли работают на боевой базе: **их нужно сменить и убрать из файлов**. До этого тестовые учётные записи считаются скомпрометированными.
- Секреты (`DB_PASSWORD`, `BACKUP_DB_PASSWORD`, `JWT_SECRET`, строки подключения) храните только в переменных окружения или в менеджере паролей.
- Роль бэкапа обходит RLS и имеет доступ ко всем данным. Пароль роли `postgres` в переменных окружения — привилегированный доступ; стоит периодически менять.
- `backend/start.js` не использовать: старый мок-сервер с секретом по умолчанию. Образ бэкенда собирается из `backend/Dockerfile`.
